# FPSO Data & AI Assistant

A learning project where I build a small data and AI workflow on top of operational data from a fictional FPSO fleet: from messy raw sensor data, to clean data in a database, to metrics in SQL and an LLM that analyses the results.

> **Note:** All data in this project is synthetic. It is generated by `generate_data.py` to look like realistic offshore equipment data (temperature, vibration, pressure, failures and maintenance logs). No real company data is used.

## What the project does

| Step | File | What it does |
|---|---|---|
| 1. Generate data | `generate_data.py` | Creates synthetic, deliberately messy sensor data for 12 pieces of equipment on 3 FPSOs over 60 days |
| 2. Explore | `explore.py` | Inspects the raw data to find data quality problems |
| 3. Clean | `clean.py` | Python/pandas pipeline that fixes the problems and saves clean data |
| 4. Database & metrics | `database.py` | Loads the data into SQLite and calculates availability and downtime with SQL |
| 5. LLM analysis | `first_llm.py` | Sends facts from the database to an LLM API and asks it to prioritise failures |

## Data cleaning

While exploring the raw data, I found five problems. This is how the pipeline handles them:

| Problem | Solution |
|---|---|
| Timestamps in two formats (`2026-08-01 13:00:00` and `01.08.2026 13:00`) | Parse both formats explicitly |
| Duplicated rows | Removed (after fixing timestamps, so duplicates in different formats are also caught) |
| Sensor glitches logged as `9999` | Set to missing, so they don't distort averages |
| Some temperatures logged in Fahrenheit | Converted to Celsius using the unit column |
| Missing values | Short gaps (max 3 hours) filled by interpolation per equipment; longer gaps are left empty rather than inventing data |

**Result:** 17,430 raw rows → 17,130 clean rows. 300 duplicates removed, 120 glitches removed, 514 Fahrenheit values converted, and 631 of 633 missing values filled.

## Metrics in SQL

Availability per vessel is calculated in SQL with the following definitions:

- **Period:** hours from the first to the last reading
- **Downtime:** sum of unplanned downtime from failure events
- **Availability:** (total time − downtime) / total time

| Vessel | Failures | Downtime (h) | Availability |
|---|---|---|---|
| FPSO Borealis | 3 | 78 | 98.65 % |
| FPSO Corona | 2 | 66 | 98.85 % |
| FPSO Aurora | 1 | 6 | 99.90 % |

A metric is only useful if everyone agrees on the definition. For example, planned maintenance is *not* counted as downtime here, which is a choice that should be agreed with the engineers using the numbers.

## LLM analysis

`first_llm.py` uses an OpenAI-compatible LLM API (Groq, model `openai/gpt-oss-120b`). SQL extracts the failure data from the database, and the LLM is asked which vessel and failure type should be prioritised. The system prompt tells the model to base its answer on the numbers provided and not to invent data.

**Design choice:** the LLM never sees the raw database. Python and SQL compute the facts first, and the LLM only reasons over those facts. This keeps the numbers correct and makes the answer easy to check.

**What I found when checking the answer against the data:**
- All numbers the model used were correct.
- It argued that the power generator was the most critical equipment. This is reasonable, but it comes from the model's general knowledge, not from the data.
- It missed a pattern: FPSO Borealis has **two** seal leakage failures, which could point to an underlying problem.

This shows why LLM output should always be validated against the underlying data.

## How to run

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

python3 generate_data.py   # create the synthetic data
python3 explore.py         # inspect the raw data
python3 clean.py           # clean the data
python3 database.py        # load into SQLite and calculate metrics
```

To run the LLM analysis, create a free API key at [console.groq.com](https://console.groq.com) and add it to a file called `.env`:

```
GROQ_API_KEY=your-key-here
```

Then run:

```bash
python3 first_llm.py
```

The `.env` file is listed in `.gitignore`, so the API key is never uploaded to GitHub.
